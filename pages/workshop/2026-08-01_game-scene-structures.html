Game Scene Structures

Writeup • Code • August 1, 2026 by hutner

Overview

There are numerous ways a project can be structured. This is mostly me going through a couple of them and coming up with what I think is the best way to go about it.

They boil down to a few ideas:

  • Main scene with everything loaded into it
  • Scene switching (modular)
  • Scene switching (globals)

Main Scene Always Loaded

This works because while you can switch scenes, there are usually things you always want to keep loaded. HUD, other UI, etc.

This approach is focused around having a main scene and then loading what you need into it. This avoids the problem of using globals, since you have your always-present stuff right in the main scene.

Overall, in this approach, the main scene acts more like a scene container where you can load and unload scenes without deleting everything in the tree.

One of the biggest downsides of this is that it isn't very lightweight. It's also extremely coupled, since scenes can't even consider running on their own - they rely on being inside this container. 

GameController (Node)
    World (Node2D)
    GUI (Control)
        SplashScreenManager (Control) # this is for an example

Below is an example of how this might be implemented. 

# make this a global/autoload script, e.g. global.gd
extends Node

var gameController: GameController
class_name GameController extends Node

@export var world: Node2D
@export var gui: Control

var currentWorld: Node2D
var currentGUI: Control

func _ready() -> void:
	Global.gameController = self
	currentGUI = $GUI/SplashScreenManager

func changeGUIScene(newScene: String, delete: bool = true, keepRunning: bool = false) -> void:
	if currentGUI != null:
		if delete:
			currentGUI.queue_free() # remove entirely
		elif keepRunning:
			currentGUI.visible = false # just make it invisible
		else:
			gui.remove_child(currentGUI) # keep in memory, does not run
	var newGUI = load(newScene).instantiate()
	gui.add_child(newGUI)
	currentGUI = newGUI

func changeWorld(newScene: String, delete: bool = true, keepRunning: bool = false) -> void:
	if currentWorld != null:
		if delete:
			currentWorld.queue_free() # remove entirely
		elif keepRunning:
			currentWorld.visible = false # just make it invisible
		else:
			world.remove_child(currentWorld) # keep in memory, does not run
	var newWorld = load(newScene).instantiate()
	world.add_child(newWorld)
	currentWorld = newWorld

Scene Switching (Modular)

In a perfect world, this is the best solution. Each scene is able to run on its own, completely decoupled from the rest of the game. The problem is that this is unlikely in many games.

This approach probably works fine for a level-based game like a puzzle platformer, but falls apart when there's some sort of data that needs to always be present.

To imagine an implementation of this, you could have a Main Menu scene, Settings, Level 1, etc., each swapped in directly with no shared container.

Overall, if state needs to exist between different scenes, this fully decoupled approach falls apart and just isn't that possible.

Scene Switching With Globals

This is the above approach, but it additionally uses globals as something like glue to keep it together. For a lot of games, this is likely the best approach, especially if the amount of data that needs to be kept is small.

To implement this, you could simply create a general Bus global which stores all of the data that needs to be shared, or maybe more individual ones like Player. It depends on your needs.

Scene Switching With Data Passing

This, again, is very similar to the two above, but utilizes something like a change_scene function to pass along specific data. This keeps the globals clean, but still suffers from the problem of not being entirely self-contained.

Conclusion

If you're creating a game with no data that needs to be persistent, and each scene can be structured entirely independently, then the simplest and cleanest way to do it is by just changing scenes directly.

If you're creating a game that requires some sort of data to be persistent across scenes, there are 3 approaches you can take:

  1. Passing data between scenes: Likely the worst approach out of these three. It's the least reliable and requires a lot of setup in the area of passing data around through functions, etc.
  2. Storing and referencing data: Putting the data you need in a file/global script that all of the levels have access to and can reference to get what they need. This way you can still have generally self-contained levels, and they have a way to get the data they need. Be careful of over-reliance on the global scripts.
  3. Loading and unloading: While this approach means the levels aren't self-contained - they can't function outside of their main parent container - it's probably the best approach for when there's a large amount of data around. If the cost of keeping track of data outweighs the cost of loading and unloading, this is likely the best approach.

TL;DR

  • If there's no persistent data and each scene can be self-contained, using a simple change_scene is the best approach.
  • If you have a little to a normal amount of persistent data, you should store your data in a global/file and reference it.
  • If your game has tons and tons of data, you should store everything in a main scene, and load/unload the parts that need to change.
