Game Scene Structures

Writeup • Code • August 1, 2026 by hutner

Overview

Problem: how should you organize the main structure of a game to reduce unnecessary duplication, keep systems decoupled, and minimize global state?

There are near infinite ways to structure a project, but there are a few common patterns I've seen others use, and have used myself. I want to go through a few of them and talk about the pros and cons of each.

This is about project structure, but specifically about the different ways a game can handle its main scene, or its levels if it has them. They boil down to a few ideas:

  • Game.tscn: loading and unloading map data
  • Game.tscn: loading and unloading scenes
  • change_scene() with globals patching it together
  • change_scene() with data passing

The Problem Restated

Imagine a puzzle game with 5 levels. How would you organize this game? You've probably thought of one of the two structures below. 

Main Menu -> Level 1 -> Level 2 -> Level n -> End
Main Menu -> Game -> End

The Data Problem

Imagine you have data that's relevant to each level. Take a chess puzzle: only the board data matters, and there's no state that needs to carry over between puzzles.

Now imagine a puzzle game with 5 levels, where the player has 5 abilities to solve the puzzles, and each time they finish a level they lose whichever ability they used the most. That's state that has to be passed from level to level for the game to keep making sense.

Level Representations

There are two main ways to represent a "level":

  1. The level is saved to disk as level data
  2. The level is its own unique level_n.tscn scene file

Level data on disk works considerably better for something like a chess puzzle. The flow would be: load the level data from disk, and use it to repopulate a world node that's already in the tree, rather than instantiate a new scene per level. This fits naturally with Game.tscn Approach: Loading & Unloading Map Data, below.

Representing a level as its own scene file works better for games where levels are more varied and different from each other (think something like Mario). This is what is primarily being discussed in this workshop.

Game.tscn Approach: Loading & Unloading Map Data

The first way to use a persistent Game.tscn container is to never actually swap child scenes at all. This is the level data stored on disk representation: you keep a single, reusable world node in the tree, and each "level" is just data (a resource, dictionary, save file, etc...) that gets loaded from disk and handed to that node, which rebuilds itself (clears the tilemap, respawns entities, resets whatever state the level needs) rather than a whole new scene getting instantiated. 

func load_level(data: LevelData) -> void:
	var current_level_data = data
	# load tile map
	# place entities
	# etc...

func unload_level() -> void:
	current_level_data = null
	# reset tile map
	# queue free entities
	# etc...

This is lightweight compared to instantiating a whole new scene per level, since you're reusing the same node structure and just changing the data that drives it. It works especially well when levels share a common shape, like grid puzzles, chess boards, etc... The problem is that it falls apart once levels stop being structurally similar.

Game.tscn Approach: Loading & Unloading Scenes

This works because while you can switch scenes, there are usually things you always want to keep loaded, like the HUD, managers, or other UI.

This approach is focused around having a main scene, then loading what you need into it. This avoids leaning too heavily on globals, since the stuff that always needs to be present already lives right in your main scene and can be handed in as a dependency to whatever you load, instead of reached for through an autoload.

Overall, in this approach, the main scene acts more like a container: you can load and unload scenes without deleting everything in the tree.

One of the biggest downsides of this is that it isn't very lightweight. It can also lead to tight coupling, since some scenes may rely on the existence of this parent container and aren't able to run entirely on their own.

Code Example

GameController (Node)
    World (Node2D)
    GUI (Control)
        SplashScreenManager (Control) # this is for an example
    MusicManager
    etc...

Below is an example of how this might be implemented. Nothing here needs to be global: anything that needs to trigger a scene change gets a direct reference to the GameController, wired up either with @export in the editor or passed in through a setup call when it's instantiated. That keeps every dependency explicit and visible. 

class_name GameController extends Node

@export var world: Node2D
@export var gui: Control

var current_world: Node2D
var current_gui: Control

func _ready() -> void:
	current_gui = $GUI/SplashScreenManager

func change_gui_scene(new_scene: String, delete: bool = true, keep_running: bool = false) -> void:
	if current_gui != null:
		if delete: current_gui.queue_free() # remove entirely
		elif keep_running: current_gui.visible = false # just make it invis
		else: gui.remove_child(current_gui) # keep in memory, not running

	var new_gui = load(new_scene).instantiate()
	gui.add_child(new_gui)
	current_gui = new_gui

func change_world(new_scene: String, delete: bool = true, keep_running: bool = false) -> void:
	if current_world != null:
		if delete: current_world.queue_free() # remove entirely
		elif keep_running: current_world.visible = false # just make it invis
		else: world.remove_child(current_world) # keep in memory, not running

	var new_world = load(new_scene).instantiate()
	world.add_child(new_world)
	current_world = new_world

change_scene() Without Data

In a perfect world, you'd just call change_scene() and let each scene run entirely on its own, fully decoupled, with no container and no shared state.

That's very clean, but it is often unreasonable: the moment any state needs to persist across the swap, calling change_scene() alone isn't enough, since it throws away the entire previous tree. You need some way to patch state back together across that gap.

change_scene() With Data

In the case you have individual scenes and also need some sort of data to persist, there are 2 main ways you can achieve this.

Using Globals/Autoloads

For a Game Jam or some testing sample project, this is likely the best approach. While it utilizes a lot of globals (which is often a bad idea), it would definitely work and is very simple and painless to setup.

To implement this, you could simply create a general Bus global which stores all of the data that needs to be shared, or maybe more individual ones like Player. It depends on your needs. 

# in player.gd
func _ready():
	Bus.player = self
# wherever you need player
func hurt():
	Bus.player.take_damage(5)

Passing Another Way

This, again, is very similar, but utilizes a custom change_scene(data) function to pass along specific data instead of reaching through a global. This keeps the globals clean, but still suffers from the problem of scenes not being able to run entirely on their own.

The swap function that instantiates the new scene, hands it data directly, then swaps it into the tree. The receiving scene just needs to expose an entry point like initialize(). 

# scene_switcher.gd (can be a plain function, doesn't have to be an autoload)
func change_scene_with_data(scene_path: String, data: Dictionary = {}) -> void:
	var new_scene = load(scene_path).instantiate()

	if new_scene.has_method("initialize"):
		new_scene.initialize(data)

	get_tree().current_scene.queue_free()
	get_tree().root.add_child(new_scene)
	get_tree().current_scene = new_scene
# level_2.gd
func initialize(data: Dictionary) -> void:
	remaining_abilities = data.get("abilities", [])
	score = data.get("score", 0)
# called from wherever the transition happens, e.g. level_1.gd
func _on_level_complete() -> void:
	change_scene_with_data("res://level_2.tscn", {
		"abilities": remaining_abilities,
		"score": score,
	})

The tradeoff is that whatever triggers the swap needs a reference to change_scene_with_data() itself (an autoload, or passed in), and the receiving scene still has to know what shape of data to expect.

change_scene() Caveats

One thing to note about the two change_scene() solutions is that both of these suffer from a duplication or global reliance problem.

For example, each scene likely needs a ton of the same things. AudioPlayer would likely be existing in each level. There are things you can do to mitigate this problem such as wrapping all the duplicated stuff in a single tscn and putting that in the level_n.tscn, but this creates an additional layer to work through. Either way, it involves some boilerplate each time you create a new level scene.

Or... instead of doing that, you can just make some of these globals (which is generally a bad practice!).

For this reason, I tend to lean towards the main Game.tscn solutions above. 

Level_n (Node2D)
| Entities (Node)
| AudioManager (Node)
| SpawningManager (Node)
...

Conclusion

If you're creating a game with no persistent data and each scene can be structured entirely independently, the simplest and cleanest way to do it is by just changing scenes directly, with no globals and no container.

Despite that, a Game.tscn with everything you need in it is likely the most sustainable, scalable, and best practice way to do it.

No persistent data, each scene runs entirely on its own → plain change_scene(), no container, no globals. Simplest and cleanest option, but only works as long as nothing needs to survive the swap.

Some persistent data, nothing needs to keep running across the swap → change_scene() with data. Globals (a Bus style autoload) are the fastest way to wire this up and are fine for a jam or prototype; passing data explicitly through a custom change_scene(data) avoids the global but each scene still can't run fully standalone.

Levels are structurally similar and can be represented as data → Game.tscn loading/unloading map data. Keep one reusable world node in the tree and rebuild it from level data on disk instead of instantiating a new scene each time.

Levels are structurally different from each other, or things need to keep running across the swap (HUD, music, managers) → Game.tscn loading/unloading scenes. Heavier and more tightly coupled to the container, but generally the most sustainable and scalable option.
